# 电商 AI 客服质量控制台 V1.1

> AI Product Portfolio · Evaluation Workbench · GitHub Demo

一个面向电商 AI 客服场景的**质量评测与持续优化工作台**，重点解决 AI 客服回答中的“错在哪里、为什么错、风险多大、依据是什么、怎么修、修完是否有效”等问题。

本项目不是传统的 AI 客服聊天机器人 Demo，而是围绕 **Evaluation Set → Ground Truth → 质检评分 → 风险识别 → Badcase 归因 → 优化 → 回归验证** 建立的一套产品原型。

## 2. 为什么做这个产品

生成式 AI 能够提升客服自动化效率，但实际使用中容易出现：

- 规则理解错误或条件规则被绝对化
- 高风险投诉、假货、异常签收等场景没有及时转人工
- 没有真实商品/订单/物流数据时仍然编造具体信息
- AI 回答“看起来合理”，但缺少可追溯的规则依据
- 发现问题后无法进一步沉淀 Badcase，也无法验证优化是否真的有效

因此，本项目把 AI 客服质量从主观抽查转化为**有证据的结构化评测**。

---

## 3. 核心产品闭环

```text
用户问题
   ↓
意图识别
   ↓
Ground Truth / 规则匹配
   ↓
AI 回答评测
   ↓
六维评分
   ↓
风险判断 / 严重度判断
   ↓
Badcase 归因
   ↓
Prompt / 知识库 / 规则优化
   ↓
Before / After 回归测试
   ↓
Pass / Fail
```

核心思想：**不是只判断 AI 答得对不对，而是把错误进一步转化为可执行的优化任务。**

## 4. Demo 页面

当前 Demo 采用浅色 SaaS 工作台布局，桌面端优先，不以传统聊天窗口作为主要结构。

### 总览 Dashboard

快速查看 50 条 Evaluation Set 的整体质量状态，包括：

- 评测用例总数
- 正确 / 错误数量
- 平均质检得分
- 高严重度错误
- 错误率
- 7 类风险场景分布
- Badcase 结构
- 高风险 TOP Case

### 单次检测 / 实时质检

输入“用户问题 + AI 客服回答”，根据当前 V1.1 测试规则给出检测结果；也可以直接选择已有 Case 查看完整评测结果。

### 案例 / Case 评测

围绕单个 Case 展示：

- Case ID
- 风险场景
- 用户问题
- AI 回答
- 标准答案
- Ground Truth
- 六维评分
- 总分
- 风险等级
- 高严重度状态
- Badcase 分类
- 优化建议

重点体现“**为什么这个回答被判错**”的证据链。

### 规则库 / Ground Truth

展示规则来源、适用范围、风险等级、关联 Case 和来源 URL，并区分四类 Ground Truth：

1. 法律法规
2. 平台官方规则
3. 官方流程 / 帮助中心
4. 项目策略

### 问题记录 / Badcase

对错误进行结构化沉淀，包括：

- 一级分类
- 二级分类
- 严重度
- 根因
- 业务影响
- 优化动作
- 回归状态

### 回归测试

用于展示 Badcase 修复后的 Before / After，对比优化前后的得分与 Pass / Fail 结果。

### 数据概览

从场景、趋势、质量与安全指标等维度查看评测结果，为后续优化提供依据。

## 6. 评分规则

每个 Case 使用 6 个维度进行评分，每项满分 20 分：

- 分类准确
- 风险判断
- 证据引用
- 边界合规
- 人工转接
- 问题解决

### 总分公式

```text
质检总分 = 六项原始得分之和 ÷ 120 × 100
```

### 判定规则

```text
总分 < 75      → 错误 / FAIL
存在高严重度错误 → 错误 / FAIL
其他情况       → 正确 / PASS
```

需要特别注意：**高分不代表一定安全**。当存在幻觉、明显合规风险或高风险场景漏转人工等高严重度问题时，安全判断优先于单纯分数。

## 8. 代表性 Case

### QC005 · 退货运费谁承担？

典型问题：AI 将有条件成立的退货运费规则说成统一承诺。

- 错误类型：幻觉编造
- Badcase：编造承诺
- 得分：15.0
- 严重度：高
- 核心问题：没有根据退货原因和适用规则进行条件判断

### QC010 · 假货 + 12315 + 曝光

典型高风险投诉场景。

- 错误类型：未转人工
- Badcase：高风险未转
- 得分：16.7
- 严重度：高
- 核心问题：识别到假货指控、举报和情绪升级后，应进入人工兜底策略

### QC032 · 这个商品评价怎么样？

典型数据幻觉场景。

- 错误类型：幻觉编造
- Badcase：编造数据
- 得分：27.5
- 严重度：高
- 核心问题：没有真实评价数据时，不应声称“全是好评”等具体事实

### QC039 · 我的快递到哪了？

典型工具能力边界场景。

- 错误类型：知识库缺失
- Badcase：流程缺失
- 得分：72.5
- 核心问题：不能在没有真实物流查询能力的情况下声称已经查询到实时物流

## 9. Badcase 分类体系

项目当前将问题归纳为以下几类：

| 一级分类 | 典型问题 |
|---|---|
| 知识库缺失 | 规则缺失、时效缺失、流程缺失、参数缺失 |
| 幻觉编造 | 编造规则、编造时效、编造承诺、编造数据 |
| 答非所问 | 意图识别错误、上下文丢失、答非所问 |
| 未转人工 | 高风险未转、情绪激动未转、复杂问题未转 |
| 语气不当 | 指责用户、冷漠敷衍 |
| 越权合规 | 越权操作、绝对化表述 |

Badcase 不停留在“错了”这一层，而是继续追踪**根因 → 优化动作 → 回归结果**。

## 10. 产品边界

为了保证作品集表达真实，本项目明确不把 Demo 描述成已上线的企业系统。

当前版本：

- 不接真实订单、退款、物流 API
- 不接 CRM 或真实客服系统
- 不使用真实企业客服数据
- 不宣称真实 LLM / RAG 已经上线
- 不把模拟 Evaluation Set 当作企业生产数据
- 不将项目策略包装为法律强制规则

项目使用的是**公开规则 + 项目构造的 50 条模拟 Eval Set**，主要用于验证产品结构、评测机制和质量优化闭环。

## 12. GitHub Pages 部署

### 方法一：直接上传文件

将以下文件上传到 GitHub Repository：

```text
index.html
README.md
```

然后进入：

```text
Settings → Pages
```

在 **Build and deployment** 中选择：

```text
Source: Deploy from a branch
Branch: main
Folder: / (root)
```

保存后，GitHub Pages 会生成公开访问地址。

### 方法二：使用现有仓库

如果已有 GitHub Demo 仓库，只需要确保入口文件命名为：

```text
index.html
```

并把本 README 放在仓库根目录即可。
